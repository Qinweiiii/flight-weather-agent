# 面试准备手册（字节 AI Agent / 全栈方向）

> 本文保留通用面试练习。当前项目实现、实跑成绩与能力边界以 [简历逐项核对](interview-defense.md) 和 [评测报告](agent-evaluation-report.md) 为准；不要引用旧示例中的未验证成绩。

> 目标：把高频问题讲成“有结构、有取舍、有数据”的答案，而不是背概念。

## 使用建议

- 每题按“结论 -> 方案 -> 结果 -> 反思”回答。
- 回答尽量控制在 45-90 秒，追问再展开细节。
- 涉及你当前项目时，保持真实：当前架构是 **workflow 编排 + 反射纠错 + 质量治理**，不是完整 Plan-and-Execute/ReAct。

## 一、必问面试题（按面试环节分类）

## 1）自我介绍 & 项目深挖

### Q1. 3分钟讲清你的航空运营诊断 Agentic BI：架构、你的贡献、难点、数据效果。

**A：**
我做的是一个面向航空公司/机场运营团队的 Agentic BI 与运营诊断系统，目标是把“自然语言问题”稳定转成“可执行查询 + 可解释结论 + 可追踪证据”。它不是乘客实时查票助手，而是面向历史运营复盘、异常诊断、天气影响归因和行业基准对比。

- 架构：采用 LangGraph 工作流编排。主控 MasterAgent 负责 Guardrail、安全检查、任务规划、意图识别与路由；执行层有 SQLAgent、SearchAgent、AnalysisAgent；治理层有 Critic 与 Debate；记忆层有短期会话记忆和长期记忆。
- 我的核心贡献：
  - 做了 SQL Reflection 自动纠错闭环（失败后带错误反馈重写 SQL 并重试）。
  - 做了时间锚点机制，把“最近 N 天”锚定到数据集最大日期，避免历史数据误读。
  - 做了证据分层与裁决（strong/proxy/none + scorecard + low-evidence 降级）。
  - 做了长期记忆的向量召回改造（向量主路径 + 关键词兜底）。
  - 做了 SSE 可观测输出（plan/trace/sql/sources/quality/chunk）。
  - 新增轻量 Skill Registry，把 SQLTool、SearchTool、ChartTool、AnomalySkill、WeatherImpactSkill、ReportSkill 的输入输出和权限边界声明出来。
- 主要难点：
  - LLM 输出不稳定导致格式错误、SQL 执行失败。
  - 外部证据不足时容易“硬对标”。
  - 多环节调用导致时延和失败定位复杂。
- 效果：
  - 系统可以稳定支持 SQL 查询、分析、搜索联动。
  - 出现低证据时不乱答，能给结构化降级结论与补证建议。
  - 端到端可追踪，定位问题更快，演示稳定性明显提升。

---

### Q2. 你为什么用 LangGraph + MCP？MCP 在项目里解决什么问题？

**A：**
- LangGraph 解决的是“可控编排”：节点清晰、状态可追踪、条件路由明确，适合生产化治理。
- MCP 解决的是“SQL执行解耦”：
  - LLM 负责生成 SQL，MCP 独立服务负责执行 SQL。
  - 执行器可独立加权限、审计、超时、隔离策略。
  - 失败信息结构化返回，便于 Reflection 做自动修复。
- 这比把 SQL 执行直接写在同一模块更易运维、更安全。

---

### Q3. 多 Agent 协作：主 Agent / 子 Agent / Critic / Debate / Guardrail 分别做什么？

**A：**
- MasterAgent：总控，负责 Guardrail -> Planner -> Intent -> 路由 -> 汇总。
- SQLAgent：NL2SQL、只读校验、MCP执行、失败反射纠错。
- SearchAgent：联网检索、领域相关性过滤、证据门控。
- AnalysisAgent：对结构化结果做洞察与图表配置。
- CriticAgent：对草稿答案做 rubric 审校与轻改写。
- DebateAgent：对“内部SQL证据 vs 外部搜索证据”打分裁决，给出 proceed/proceed_with_caveat/low_evidence。
- GuardrailAgent：执行前拦截注入式和高风险请求。

---

### Q4. SQL 自动纠错怎么做？重试机制、时间锚点、MCP 解耦讲清楚。

**A：**
- 第一轮：根据 schema + few-shot 生成 SQL。
- 执行前：只读安全校验，拦截非 SELECT/CTE、多语句与高危关键词。
- 执行：通过 MCP SQL 服务执行，不在 LLM 侧直接跑 SQL。
- 失败后：把原 SQL + 错误信息反馈给 LLM，生成修复 SQL，再执行。
- 重试：最多 3 次，记录 retry_count 与 failure_stage 便于追踪。
- 时间锚点：把 now/current_date 替换为数据最大日期，保证“最近N天”基于数据观测期。

---

### Q5. 你的双层记忆（短期 + 长期向量检索）怎么实现？

**A：**
- 短期记忆：会话级消息保存在图状态（checkpointer），用于当前多轮上下文。
- 长期记忆：SQLite 持久化两类信息：
  - 用户偏好（key-value，精确读取）
  - 用户知识（文本 + confidence + embedding）
- 检索策略：
  - 相关知识优先走向量相似度召回。
  - 分数过低时走 LIKE 兜底，避免冷启动召回空。
- 生效时机：
  - 请求中：召回长期记忆注入意图识别上下文。
  - 请求后：从对话中自动抽取偏好与知识并写回。

---

### Q6. 食刻运营中台：Redis 缓存、消息队列、幂等、性能优化讲细节。

**A（可按你真实经历替换字段名）**：
- Redis：
  - 热点数据缓存（商品、活动、门店配置），设置合理 TTL。
  - 防穿透：空值缓存 + 参数校验。
  - 防击穿：热点 key 加互斥锁/单飞。
  - 防雪崩：TTL 加随机抖动 + 多级降级。
- MQ（RabbitMQ）：
  - 订单/库存异步解耦，削峰填谷。
  - 开启消息确认与重试；失败入死信队列。
  - 消费端按业务主键做幂等（唯一约束/幂等表/去重键）。
- 幂等：
  - 对“创建类接口”使用业务唯一号 + 乐观锁/唯一索引。
- 性能优化：
  - 先做慢查询治理（索引、覆盖索引、SQL改写）。
  - 接口拆分同步/异步链路，降低主路径时延。
  - 核心指标看 P95/P99、缓存命中率、错误率。

---

### Q7. Agent 落地最大坑是什么？怎么解决幻觉、死循环、超时、格式错误？

**A：**
- 幻觉：
  - 强制“证据驱动回答”，低证据降级，不给确定性结论。
- 死循环：
  - 反射重试上限（如 SQL 最大 3 次）+ 明确停止条件。
- 超时：
  - 子任务隔离，超时返回可降级结果，不阻塞整条链路。
- 格式错误：
  - JSON 清洗、代码块剥离、解析失败多层 fallback。
- 关键理念：优先保证系统“可控失败”，而不是“偶尔惊艳”。

## 2）Agent 核心原理（腾讯高频）

### Q8. ReAct 核心循环：Think → Action → Observation 每一步怎么实现？

**A：**
标准 ReAct 是：
- Think：模型先推理下一步。
- Action：调用工具。
- Observation：拿到工具结果再继续推理。
- 循环直到满足停止条件。

我当前项目是工程化工作流变体，不是完整 ReAct 自由循环：
- 用固定节点和条件路由替代开放式循环。
- 在关键步骤做工具调用与观测（SQL执行、搜索、裁决）。
- 用重试上限与状态控制避免无限调用。

---

### Q9. Function Calling 与 Agent 的区别？

**A：**
- Function Calling：模型调用一次或少量工具，重点是参数结构化。
- Agent：包含目标分解、工具选择、状态管理、失败恢复、停止条件。
- 关系：Function Calling 是 Agent 的能力组件，不等于完整 Agent 系统。

---

### Q10. RAG 与 Agent 的区别？Agent 怎么用 RAG？

**A：**
- RAG：检索外部知识后让模型生成，核心是“补知识”。
- Agent：核心是“决策与执行”，可调用多种工具。
- Agent 用 RAG：把检索当成工具之一，先决策是否检索，再把结果并入证据链进行裁决与回答。

---

### Q11. Agent 怎么减少幻觉？

**A：**
- 证据优先：没有证据就降级，不强答。
- 结构化约束：输出格式和评分卡约束。
- 工具结果优先：回答尽量引用工具结果中的事实与数值。
- 分层治理：Guardrail（前置）+ Debate/Critic（后置）。

---

### Q12. 如何设计停止条件，避免死循环 / 无限调用？

**A：**
- 设硬上限：如 SQL 反射最多 3 次。
- 设状态终止：命中错误阈值直接进入降级回答。
- 设路径终止：每个意图只走一条明确链路，最后汇总结束。
- 设超时终止：单节点超时后返回 fallback。

---

### Q13. 多 Agent 协作优缺点？什么时候单 Agent，什么时候多 Agent？

**A：**
- 多 Agent优点：分工清晰、可治理、可扩展、可观测。
- 多 Agent缺点：架构复杂、调试和状态管理成本更高。
- 选型建议：
  - 单 Agent：需求简单、工具少、上线快。
  - 多 Agent：高风险场景、需要安全/质量/证据治理、链路较长。

---

### Q14. 模型输出失败怎么分类？格式/内容/调用/逻辑自洽失败怎么兜底？

**A：**
- 格式失败：JSON 解析失败 -> 清洗代码块 -> fallback 模式。
- 内容失败：证据不足/不相关 -> 低证据降级模板。
- 调用失败：工具异常/超时 -> 错误事件 + 可降级回答。
- 逻辑失败：口径冲突/时间不一致 -> Debate 标注 caveat 并提示不可横比。

---

### Q15. 上下文怎么管理？滑动窗口、重要性、相关性、时效性取舍策略？

**A：**
- 滑动窗口：短期记忆保留近期消息；超阈值时做摘要压缩。
- 重要性：偏好和高置信知识长期保留。
- 相关性：长期记忆按语义召回 top_k 注入，不全量塞 prompt。
- 时效性：时间敏感问题优先近期上下文和最新证据。

## 3）后端 & 全栈基础（贴合 JD）

### Q16. Go/Gin 项目：接口设计、中间件、JWT、WebSocket。

**A：**
- 接口设计：REST 风格，统一响应结构（code/message/data/request_id）。
- 中间件：日志、panic recover、鉴权、限流、链路追踪。
- JWT：短期 access token + 刷新机制，服务端校验签名和过期。
- WebSocket：用于实时推送（状态变更/任务进度），心跳保活与断线重连。

---

### Q17. MySQL：索引、事务、慢查询、分库分表思路。

**A：**
- 索引：优先覆盖索引和高选择性字段，避免无效索引。
- 事务：明确隔离级别，缩短事务时间，避免长事务锁表。
- 慢查询：通过执行计划定位回表/全表扫描并改写。
- 分库分表：按业务主键或时间维度拆分，配合路由层和全局ID方案。

---

### Q18. Redis：缓存击穿 / 穿透 / 雪崩，你项目怎么解决？

**A：**
- 击穿：热点 key 互斥重建或 single-flight。
- 穿透：参数校验 + 空值缓存 + 布隆过滤器（可选）。
- 雪崩：过期时间打散 + 多级缓存 + 熔断降级。

---

### Q19. RabbitMQ：消息可靠投递、重试、死信、幂等。

**A：**
- 可靠投递：生产者 confirm + 持久化队列/消息。
- 重试：消费失败按策略重试，超过阈值进死信队列。
- 幂等：业务唯一键 + 消费幂等表/去重缓存，避免重复执行。

---

### Q20. 性能优化：P99、缓存命中率、接口耗时优化。

**A：**
- 指标体系：P50/P95/P99、QPS、错误率、缓存命中率。
- 优化优先级：先优化主路径慢点（SQL、外部调用、序列化）。
- 常用手段：缓存、并发执行、异步化、索引优化、减少冗余计算。

---

### Q21. Vue/Bootstrap 前端：你做过哪些页面？响应式怎么实现？

**A：**
- 页面：问答主界面、执行状态流、来源展示、质量评分卡、图表面板。
- 响应式：栅格布局 + 媒体查询 + 组件级断点，保证移动端可读性。
- 实时性：SSE 按事件类型渲染（status/trace/sql/sources/quality/chunk）。

## 4）场景题（腾讯最爱）

### Q22. 给腾讯文档做一个文档总结/问答 Agent，你怎么设计？

**A：**
- 架构：
  - 接入层：文档权限校验 + 请求鉴权。
  - 索引层：分片切块、向量索引、元数据过滤（空间/文档/版本）。
  - 执行层：检索 -> 证据重排 -> 生成 -> 引用标注。
  - 治理层：安全拦截、质量审校、低证据降级。
- 输出要求：必须给出处段落和版本号，避免无来源总结。

---

### Q23. 如何做权限控制，防止 Agent 越权读写文档？

**A：**
- 每次请求携带用户身份与文档 ACL。
- 检索前做“权限过滤”，不让无权限文档进候选集。
- 工具层做二次鉴权，防止绕过上层。
- 全链路审计：记录谁在何时访问了哪些文档片段。

---

### Q24. 高并发下 Agent 调用大模型限流、排队、降级怎么做？

**A：**
- 限流：按用户/租户/接口分级限流（令牌桶）。
- 排队：任务队列 + 优先级调度，避免突发打满。
- 降级：
  - 优先关闭高成本路径（如外部搜索）
  - 缩短上下文和 max_tokens
  - 返回结构化“稍后重试/低证据”结果。

---

### Q25. 如何做可观测：日志、埋点、调用链、成功率监控？

**A：**
- 日志：统一 request_id，节点级日志（intent/sql/search/debate）。
- 埋点：记录节点耗时、重试次数、失败阶段、模型调用量。
- 调用链：按一次请求串联各 agent 子调用。
- 监控面板：成功率、超时率、P95/P99、证据不足占比、降级占比。

## 二、加练高频基础题（你新增的 10 个）

### Q26. Harness Engineer 是什么？

**A：**
- Harness Engineer 通常指“测试与验证基础设施工程师”，核心是搭建自动化验证体系，而不是只写单个测试用例。
- 主要工作：
  - 设计测试框架（test harness）与基线数据。
  - 构建回归流水线（CI 中自动执行、自动对比、自动告警）。
  - 提供可复现测试环境和 Mock 能力。
  - 建立覆盖率、稳定性、失败分类等质量指标。
- 在 Agent 项目里可对应到：自动评测脚本、失败样例归档、版本回归对比、线上质量门禁。

---

### Q27. RESTful 简单介绍？编写规范？

**A：**
- RESTful 是一种基于资源的接口设计风格：通过 URI 表达资源，通过 HTTP 方法表达动作。
- 常见规范：
  - URI 用名词复数，如 `/users`、`/orders/{id}`。
  - 方法语义清晰：GET 查、POST 建、PUT 全量改、PATCH 部分改、DELETE 删。
  - 无状态：请求应自包含鉴权与上下文，不依赖服务端会话。
  - 统一响应结构：`code/message/data/request_id`。
  - 正确状态码：200/201/204/400/401/403/404/409/500。
  - 版本化：`/api/v1/...` 或 header version。
  - 幂等敏感接口配幂等键与重试策略。

---

### Q28. 消息推送除了 WebSocket 还可以用什么？为什么用 WebSocket？

**A：**
- 可选方案：
  - SSE：服务端单向推送，适合文本流（如 LLM chunk）。
  - 长轮询：兼容性高，但资源开销大。
  - 短轮询：实现简单，但实时性差、请求多。
  - MQTT：物联网场景常见。
- 选择 WebSocket 的原因：
  - 全双工、低时延、连接复用，适合高频双向交互。
  - 客户端可实时上报控制指令，服务端可持续推送状态。
- 什么时候不用 WebSocket：
  - 如果只需要服务端单向文本流，SSE 更轻、更简单。

---

### Q29. PUT 和 POST 的差别？

**A：**
- POST：通常用于“创建子资源”或触发动作，URI 一般是集合，如 `POST /orders`。
- PUT：通常用于“对已知 URI 资源做全量替换”，如 `PUT /users/{id}`。
- 语义差异：
  - POST 常见非幂等。
  - PUT 按语义应幂等（同请求重复执行结果一致）。

---

### Q30. GET 有可能不幂等吗？POST 可能幂等吗？

**A：**
- 从规范语义上：
  - GET 应是安全且幂等。
  - POST 默认非幂等。
- 但工程实现上：
  - GET 也可能被写成非幂等（例如错误地在查询接口里记一次计数并影响结果）。这属于设计不当。
  - POST 可以通过幂等键实现幂等（如支付/下单请求携带 `Idempotency-Key`，重复提交只创建一次）。

---

### Q31. 修改数据库与删 Redis 缓存，先后顺序怎么选？若删缓存失败怎么办？

**A：**
- 常用策略是“先改数据库，再删缓存”（Cache Aside）。
- 原因：
  - 如果先删缓存再改库，期间有并发读会把旧值再写回缓存，导致脏缓存回流。
- 若“改库成功但删缓存失败”：
  - 立即重试删除（含指数退避）。
  - 记录失败日志并入异步补偿队列（MQ/任务表）继续删。
  - 给缓存设置较短 TTL 兜底。
  - 关键场景可用延迟双删（写后短延迟再删一次）。

### Q32. GMP 简单解释（Go 调度模型）

**A：**
- G：Goroutine（协程）。
- M：Machine（内核线程）。
- P：Processor（调度上下文，持有可运行队列）。
- 关系：
  - M 必须绑定 P 才能执行 G。
  - 调度器在多个 P 的本地队列与全局队列之间分发 G。
- 价值：
  - 让大量协程高效复用少量线程，降低线程切换成本。

### Q33. GC 简单解释

**A：**
- GC（垃圾回收）是自动识别并回收“不可达对象”的机制，避免内存泄漏。
- 常见流程：
  - 标记（找出仍可达对象）
  - 清扫（回收不可达对象）
- Go 的 GC 是并发标记清扫为主，目标是在可接受停顿下维持吞吐与内存平衡。
- 工程上关注：
  - 降低对象分配频率、减少短命大对象、复用 buffer、观察 GC pause 与 heap 曲线。

### Q35. TCP 四次挥手里，为什么服务端 ACK 和 FIN 不一定一起发？

**A：**
- 因为 TCP 是全双工，两个方向要分别关闭。
- 当服务端收到客户端 FIN 时：
  - 先发 ACK，表示“我收到你这边的关闭请求了”。
  - 但服务端自己可能还有数据没发完，不能立刻 FIN。
- 等服务端发送完剩余数据后，再单独发 FIN。
- 所以 ACK 与 FIN 可能合并，也可能分开发，这取决于服务端当时是否还有待发送数据。

### Q36. 什么是 Skill？在 Agent 系统里怎么理解？

**A：**
- Skill 可以理解为“可复用的能力包/方法论模板”，本质是把一类任务的最佳实践沉淀成标准化流程。
- 典型内容包括：
  - 任务目标与边界
  - 触发条件（什么时候应该用这个 Skill）
  - 标准执行步骤
  - 失败处理与回退策略
  - 输出格式要求
- 在工程里，Skill 的价值是：
  - 降低不同人/不同模型输出风格波动
  - 提升复杂任务的稳定性和一致性
  - 让系统更容易扩展和维护

---

### Q37. Skill 和 Tool 的区别是什么？

**A：**
- 一句话区分：
  - Tool 是“做事的工具”
  - Skill 是“怎么做事的方法”
- Tool 更偏执行能力：
  - 例如 SQL 查询工具、搜索工具、文件读写工具。
  - 输入明确参数，输出明确结果。
- Skill 更偏策略与编排：
  - 例如“如何做代码评审”“如何做故障排查”“如何做低证据降级回答”。
  - 它决定任务步骤、先后顺序、校验标准、回退逻辑。
- 两者关系：
  - Skill 会调用多个 Tool 来完成任务。
  - Tool 不关心全局流程，只负责完成某个具体动作。

可用面试例子：
- “查询近90天航班延误率”里，SQL 执行器是 Tool；
- “先查内部数据、再查外部证据、再裁决可信度”这一整套流程是 Skill。

---

### Q38. 什么时候该强调 Skill，什么时候该强调 Tool？

**A：**
- 强调 Tool 的场景：
  - 面试官问你“具体怎么调用能力”“接口如何设计”“参数与返回是什么”。
- 强调 Skill 的场景：
  - 面试官问你“复杂任务如何稳定落地”“为什么结果一致性更好”“如何降低模型波动”。
- 最佳回答方式：
  - 先讲 Skill（流程与策略），再讲 Tool（落地执行），最后讲指标（效果验证）。
