# 航空运营诊断定位

目标用户是运营分析、运行控制及机场运行团队。核心任务是用历史样本复盘指标变化，找到值得优先调查的机场/航司与报告原因，形成有证据的行动候选和验证计划。

历史数据适合回答周期趋势、异常候选和复盘问题。它不支持回答今天某航班的实际状态，也不证明某个预案在未来有效。联网搜索用于补充背景资料与候选基准，不会让历史库变成实时系统。

主流程现在通过 `agents/workflow.py` 的同一张 LangGraph 执行：Guardrail、意图及参数路由、工具执行、汇总、Critic、Memory。计划由选定的实际执行路径生成，旧 PlannerAgent 和 ToolRouterAgent 文件保留为历史实验，不再单独生成一个可能与执行不符的“漂亮计划”。

## 诊断之后

1. 筛查最近周期相对上一等长周期的指标变化，标出有效样本及筛查限制。
2. 对报告原因按分钟排序，另列天气分组相关性，避免混淆量纲和因果。
3. 列出正延误负担较高的机场/航司组合，作为复核对象。
4. 选择人工维护的预案候选，注明责任团队、复核周期和缺失证据。
5. 展示显式假设下的分钟量级，并要求试点/对照验证；不报告已实现收益。

这形成的是“分析到验证计划”的流程。项目尚未包含现场执行、试点结果回写或真实改善效果的验证，因此不称为完整的运营执行闭环。

## 实时扩展

可以增加 FlightStatusTool、WeatherNowTool、AirportCapacityTool，将事件时间、采集时间、来源、缓存时效、限流和错误统一到工具层。实时监控需独立意图与数据新鲜度门槛，历史窗口仍用于基线。

通知/调度执行需要额外的实际业务授权及系统接入；当前实现只读分析。数据契约、评测和简历边界分别见 [data-contract.md](data-contract.md)、[agent-evaluation-report.md](agent-evaluation-report.md)、[interview-defense.md](interview-defense.md)。
