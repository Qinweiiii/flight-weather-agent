# 简历逐项核对与答辩

## 一分钟介绍

我实现了一个面向航班历史运营数据的可控多 Agent 分析工作台。主 Agent 在限定意图中选择查询、分析、联网或联合路径，LangGraph 管理执行与会话状态。NL2SQL 通过独立 MCP 服务访问只读 SQLite，失败后反馈错误做有界 Reflection。行业比较并发收集内外部证据，Debate 在时间、来源、口径不足时拒绝确定性结论。前端 React 通过 SSE 展示执行过程、SQL 和图表。

我后来补了运营诊断场景：同口径异常筛查、报告原因分解、带责任团队和验证步骤的行动候选。重点是把数据证据变成可复核的分析任务，不声称能直接优化航班调度。

## 简历与实现

| 简历描述 | 实际实现 / 可展示证据 | 不应扩张的说法 |
|---|---|---|
| LangGraph 多 Agent 路由 | workflow.py 的 guardrail→intent→execute→summarize→critic→memory；真实模式模型返回意图与参数 | 不说无限自主规划，也不说 YAML 本身会自主执行 |
| SQL / Analysis / Search | 独立职责类，主流程调用；联合路径线程池真正同时启动 SQL 与搜索 | 不把每个工具都称为自治 Agent |
| Guardrail / Critic | 输入规则+模型判断；生成答案结构化审校；确定性 skill 报告显式标记模板检查 | 不说 Guardrail 可防住所有提示攻击，不把评分当事实真值 |
| MCP SQL 解耦 | stdio 启动独立 Python 服务，工具 execute_sql，路径通过环境显式传入 | 固定统计 skill 直接使用共享只读模块，不说它们都经 MCP |
| Reflection | 原 SQL + schema + 错误反馈；额外 N 次上限；attempts 可追踪 | 纠错成功案例使用 scripted LLM 回归，不能充当真实模型修复率 |
| 并行 Search + SQL + Debate | 两个 future 内分别启动任务；并发屏障测试；硬证据门槛优先于软分数 | 搜索来源多不等于统计口径一致；当前默认无法自动认证搜索摘要的分母 |
| SSE 实时过程 | custom stream writer 发送节点状态、SQL、来源、chart、quality；done 最后 | 不说最终答案逐 token 输出，目前先审校后发送 |
| 长短期 Memory | MemorySaver 会话内 checkpoint + SQLite 显式偏好；哈希向量+关键词召回 | 不是深度语义 embedding，不把模型结论自动保存成业务事实 |

## 为什么有业务意义

运营分析首先帮助确定复核优先级。例如虚拟数据中 AAA 的报告天气原因突出，而 BBB/ZX 是前序晚到传播突出；建议的调查对象与证据需求不同。CCC 的取消上升则应单独跟踪，不能因取消记录没有 ARR_DELAY 就把它当准点。

真实历史库最近 30 天的运行检查中，前序晚到和航司报告原因分钟高于天气原因，因此无需捏造额外数据也能避免“结论永远是天气不好”。这些只是样本中的报告分类，不是因果证明。

## 常见追问

**为什么不用普通 BI？**
固定报表仍然更适合稳定重复指标。Agent 的增量在于把自然语言问题路由到不同证据源，执行可追踪的工具链，处理 SQL 错误和证据不足，并组合解释。固定指标计算留给确定性工具，避免让 LLM 自己算数。

**为什么用这么多 Agent？**
它们是职责划分与独立评测单元，不是越多越聪明。输入风险、查询执行、外部来源、结果审校失败模式不同。实现保留有限路径；复杂度是否值得，要用失败阶段与延迟记录判断。

**建议真的能减少延误吗？**
没有证明。当前输出的是人工维护预案匹配和假设情景；需要尾号、机组、保障/容量数据及试点对照。项目没有报告真实节省效果。

**评测准确率多少？**
先展示 `eval/results/` 的实跑记录。本轮完成离线工程回归，模型 Key 不在执行环境，未报告真实 NL2SQL 准确率。Golden set 验证脚本、失败阶段、纠错案例和结果比较器均已准备好。

**虚拟数据是不是造假？**
它是明确标注的测试夹具，用于验证已知异常与相反场景能否被区分；真实模型成绩和真实行业结论必须使用独立评测，不混算。

**怎么接实时？**
保留事件时间、采集时间、来源和数据延迟，在同一工具层加 API adapter 和缓存/限流，再建立独立的运行监控工作流。历史样本本身不会因为联网搜索就变实时。
